# 真人数字人交互平台 PRD

**版本：** v0.1
**基线项目：** LiveTalking
**状态：** 可行性与实施规划

## 1. 产品目标

基于 LiveTalking 构建一个可配置的真人数字人，使用户可以通过文字、语音和摄像头进行自然交流。数字人具备明确角色、性格、语言和音色；用户打断后，可在同一上下文中继续交流，并可在授权范围内主动发起合适的开场、追问或提醒。

首期目标是单用户实时会话，而非无人值守客服、多房间会议或高并发 SaaS 平台。

## 2. 目标场景

| 场景 | 用户行为 | 数字人能力 | 可行性 |
| --- | --- | --- | --- |
| 品牌接待 | 文字或语音咨询 | 固定人设讲解、回答常见问题、口型同步 | 可实现 |
| 导览/培训 | 语音追问、打断后继续 | 多轮记忆、角色化回答、恢复上一话题 | 可实现 |
| 移动端陪伴 | 手机前/后摄像头、语音交互 | 浏览器摄像头预览、语音输入、实时数字人输出 | 可实现，需 HTTPS 与移动端测试 |
| 看图对话 | 对着摄像头展示物品或环境 | 抓帧、视觉模型理解、带上下文回答 | 可实现，当前未实现 |
| 多语种服务 | 切换语种/音色/方言 | 多语种 ASR、LLM、对应 TTS 声音 | 可实现，方言效果取决于模型和音色 |
| 主动接待 | 用户进入页面或长时间静默 | 按角色主动开场、追问或结束会话 | 可实现，必须有频控和关闭入口 |
| 业务提醒 | 外部系统触发事件 | 根据预约、排队、培训任务主动通知 | 可实现，需定义事件 API 与鉴权 |
| 拟人动作反馈 | 用户提问、拒答、问候、告别或做出动作 | 语音、表情、头部、手势和身体姿态协同反馈 | 基础动作可实现，实时自由动作需新增能力 |

## 3. 当前基线能力

LiveTalking 已提供以下可复用能力：

| 能力 | 当前实现 | 结论 |
| --- | --- | --- |
| 真人形象与口型驱动 | MuseTalk、Wav2Lip、Ultralight avatar 插件 | 已具备 |
| 实时输出 | WebRTC、RTMP、虚拟摄像头 | 已具备 |
| 文字交互 | `/human` 的 `echo` 与 `chat` 模式 | 已具备 |
| 语音识别 | 本地 SenseVoice/FunASR WebSocket | 已具备基础链路 |
| 语音合成 | Edge、Azure、腾讯、豆包、Qwen、XTTS 等插件 | 已具备，声音覆盖度取决于提供商 |
| LLM | DashScope / OrcaRouter OpenAI 兼容接口 | 已具备单轮流式链路 |
| 摄像头 | 浏览器本地 `getUserMedia` 预览 | 已具备前端接入，不含服务端视觉理解 |
| 人设/语言/会话上下文 | `server/dialogue.py` 和 `/persona` | 已具备最小会话内版本 |
| 打断与继续 | 停止数字人播放、会话轮次保护、继续提示 | 已具备基础版本 |
| 主动交互 | 无 | 需要新增会话事件与主动策略层 |
| 动作编排 | 自定义 `audiotype` 动作状态 | 已支持有限的预设状态切换 | 需要扩展为语义/视觉事件到动作的映射 |

当前修改涉及：[server/dialogue.py](/opt/LiveTalking/server/dialogue.py)、[server/routes.py](/opt/LiveTalking/server/routes.py)、[llm.py](/opt/LiveTalking/llm.py) 和 [web/index.html](/opt/LiveTalking/web/index.html)。

现有 `web/admin.html` 只能查看全局配置和活跃会话，不能作为运营后台使用。因此，统一管理后台是 P1 起的独立产品面，而不是在现有监控页上继续堆叠按钮。

## 4. 可实现性结论

需求整体可实现。LiveTalking 已覆盖“数字人视频生成 + 实时传输 + ASR/TTS + LLM”的主干，首版不需要替换底层数字人引擎。

需要明确两个边界：

1. 浏览器摄像头只让用户看到本地预览，不会自动让数字人“看见”。看图互动必须把摄像头帧安全上传给视觉模型，并将识别结果加入对话上下文。
2. “方言”包含识别、语言生成、语音合成三环。普通话、英语、日语和粤语可作为首批目标；上海话、闽南语等应按实际 ASR/TTS 供应商能力逐一验收，不能仅靠提示词保证自然度。

## 5. 功能需求

### 5.1 角色与人格

- 管理员可配置姓名、身份背景、语气、情绪边界、禁答范围、知识库范围、默认语言和默认音色。
- 一个会话创建时绑定一份角色配置；会话中允许管理员切换角色。
- 所有 LLM 请求必须携带角色系统提示词和最近对话历史。

**验收：** 同一问题在“亲切导游”和“严谨培训师”两个角色下，措辞与回答结构有明显差异，且不越过预设禁答边界。

### 5.2 文本与语音交互

- 用户可输入文本，或通过浏览器麦克风讲话。
- ASR 自动识别语种，文本进入同一对话流水线。
- 数字人使用配置音色说出流式回答，视频口型与音频同步。
- 保留用户原始转写和数字人回复，用于会话回放与问题排查。

**验收：** 文本、普通话语音均能触发同一角色化回复；用户可看到转写结果和当前状态。

### 5.3 打断与恢复

- 用户讲话、点击“打断”或发送新问题时，立即取消未播放音频，并令旧 LLM 流失效。
- 用户选择“继续”时，数字人根据最近一轮已生成内容接续表达，不重复已说句子。
- 后续版本采用 VAD 自动检测用户插话，替代手动按钮。

**验收：** 在数字人说话中连续打断三次，旧回答不再混入新回答；点击继续后能延续原话题。

### 5.4 摄像头与视觉互动

- 桌面浏览器、笔记本和手机均通过 `getUserMedia` 选择前/后摄像头。
- 用户明确开启后才采集视频；界面持续展示采集状态并可一键关闭。
- 首版以低频抓帧（例如用户提问或每 2 秒一帧）送往视觉模型，不上传完整视频流。
- 视觉结果仅作为当前会话上下文，不默认持久保存图像。

**验收：** 用户展示常见物品并提问“这是什么”，数字人可基于画面回答；摄像头关闭后停止帧上传。

### 5.5 多语种、音色与方言

- 语言配置控制 ASR 语言提示、LLM 回复语言和 TTS 音色选择。
- 预置并验证普通话、英语、日语、粤语各一套 ASR + TTS 配置。
- 方言作为“支持列表”管理，每个方言提供明确的 ASR、LLM 和 TTS 质量等级。

**验收：** 切换语言后，转写、回答和发音一致；不支持的方言应明确降级为文字或普通话，而非伪装支持。

### 5.6 主动交互

- 数字人可基于以下受控事件主动发言：会话连接成功、用户在场但静默、用户主动打开摄像头、用户完成业务步骤、外部业务事件到达。
- 每个角色配置开场白、追问策略、提醒模板、静默阈值、单次会话最大主动次数和静默时段。
- 主动表达必须先经过当前会话状态检查：用户正在说话、数字人正在播放、摄像头关闭、用户选择“勿扰”或达到频率上限时均不触发。
- 用户可随时打断、关闭主动交互或选择“稍后再说”；关闭状态在会话内生效，并在持久化会话上线后跨重连保留。
- 外部业务系统通过受鉴权的事件接口提交结构化事件，例如 `appointment_ready`、`training_step_due`；LLM 只能基于允许字段组织自然语言，不能自行编造业务事实。

**验收：** 用户连接后只收到一次角色化问候；静默达到阈值后最多收到一次相关追问；用户打断或关闭后不再主动发言；外部事件可在 2 秒内触发一次可解释的提醒。

### 5.7 统一管理后台

后台面向运营人员、内容管理员和平台管理员，统一管理数字人、模型、会话和运行状态。首版需包含以下模块：

| 模块 | 功能 |
| --- | --- |
| 总览 | 在线会话、错误率、端到端延迟、GPU/队列状态、今日交互量 |
| 数字人管理 | 创建、命名、描述、头像/驱动视频、默认角色、人设、语言、音色、状态（草稿/发布/停用） |
| 模型路由 | 按能力配置 LLM、视觉模型、ASR、TTS 提供商与模型；为每个数字人选择一套模型组合 |
| 音色与语言 | 管理 TTS 音色 ID、试听、适用语言/方言、默认语速和情绪；不保存未授权的声音克隆资产 |
| 会话管理 | 搜索会话、查看转写与回复、查看中断原因、结束会话、按授权导出记录 |
| 主动策略 | 配置开场白、静默阈值、业务事件模板、频率上限、勿扰时段和启停开关 |
| 日志与告警 | 查询结构化运行日志、错误堆栈、模型调用耗时、请求 ID；按错误率/延迟告警 |
| 系统设置 | 密钥引用、存储保留期、内容安全策略、角色权限、审计记录 |

**验收：** 管理员不改代码即可创建并发布一个数字人、为其选择 LLM/ASR/TTS、设定人设与主动策略；每次会话均可按请求 ID 关联到模型调用与运行日志。

### 5.8 数字人创建与配置

数字人是可发布的业务实体，不等同于底层 avatar 文件。每个数字人至少包含：

| 字段 | 说明 |
| --- | --- |
| `id` / 名称 | 稳定标识与运营名称 |
| 基础信息 | 描述、所属业务、封面、创建者、状态 |
| 形象配置 | avatar 模型、形象资产版本、驱动参数 |
| 角色配置 | 人设、语气、边界、知识库、主动策略 |
| 语言配置 | 默认语言、可选语言、方言降级规则 |
| 模型配置 | LLM、视觉、ASR、TTS 的提供商、模型和参数引用 |
| 发布配置 | WebRTC 入口、并发配额、可见范围、版本、回滚目标 |

创建流程：`创建草稿 -> 填写基础信息 -> 选择形象和模型 -> 配置角色/语言/主动策略 -> 沙盒测试 -> 发布`。发布后创建不可变版本；生产会话绑定已发布版本，避免编辑中的配置影响在线用户。

### 5.9 拟人化动作与多模态反应

数字人不能只改变台词，还应根据语义、情绪和用户行为选择匹配的动作、表情和姿态。动作输出由“事件识别 -> 反应策略 -> 动作资产 -> 音视频同步”组成。

| 触发 | 语言示例 | 期望表现 |
| --- | --- | --- |
| 无法回答 | “哎呀，这个我不知道呀。” | 轻微皱眉、摊手或耸肩、短暂停顿、语气犹豫 |
| 用户问候 | “你好，欢迎来找我。” | 微笑、点头、抬手挥手 |
| 用户感谢 | “不客气，很高兴帮到你。” | 微笑、点头、开放手势 |
| 告别 | “拜拜，下次见。” | 挥手、身体轻摆、结束停留姿态 |
| 高风险/拒答 | “这个问题我不能帮你完成。” | 收敛表情、轻微摇头、保持尊重距离 |

动作必须受角色设定约束：严肃角色减少夸张动作，儿童或娱乐角色可提高动作幅度。回答文本和动作事件使用同一请求 ID，保证“说什么”和“怎么表现”可追踪。

摄像头动作反应：用户明确授权摄像头后，视觉服务识别有人进入、面对镜头、挥手、点头、摇头、举手和离开画面等有限事件。识别结果以 `user_waved`、`user_nodded`、`user_left` 等结构化事件输入会话编排层，数字人据此挥手问候、点头确认或礼貌告别。首版低频抓帧、多帧确认且不保存连续视频。

“握手”只能呈现为数字人的伸手/握手动画与语音回应。普通摄像头无法产生真实触觉，且只能识别用户伸手或靠近的近似手势，产品不得将其宣传为物理握手。

| 等级 | 实现方式 | 可达到效果 |
| --- | --- | --- |
| L0 | 现有 `audiotype`/预录动作状态 | 固定挥手、点头、告别等有限动作 |
| L1 | 语义分类器 + 动作状态机 + 口型/TTS 同步 | “不会、欢迎、感谢、告别”等语义稳定触发匹配动作 |
| L2 | 姿态/手势识别 + 多动作素材或生成模型 | 对用户挥手、点头、离开做出条件反应 |
| L3 | 实时全身动作生成、视线、手部和接触模拟 | 更接近真人的连续互动，但成本、延迟和稳定性最高 |

**验收：** 对同一类事件连续测试 20 次，记录动作触发准确率、动作与语音起始偏差及错误动作率；无法识别时回退为自然台词和中性待机动作。

## 6. 技术方案

```text
用户文本 / 麦克风 / 摄像头
        |          |          |
        |       ASR 转写     抓帧 -> 视觉模型
        |          |          |
        +------ 会话编排层（人设、记忆、打断、权限） ------+
                                      |
                  LLM 流式角色化回答 / 主动策略触发
                                      |
                         TTS -> 数字人驱动 -> WebRTC 视频/音频
```

### 6.1 保留并扩展的模块

| 层级 | 复用组件 | 增补内容 |
| --- | --- | --- |
| 数字人渲染 | avatar、TTS、WebRTC、virtualcam | 性能压测、形象/音色资产管理 |
| 语音输入 | `server/asr_server.py` | VAD、流式转写、语言路由 |
| 对话 | `llm.py` | 取消令牌、结构化提示词、持久化记忆、知识库检索 |
| 主动编排 | 无 | 事件队列、计时器、频控、勿扰状态、业务事件 API |
| 会话 | `server/session_manager.py` | Redis/数据库、超时、并发和审计 |
| 视觉 | 无 | 摄像头帧上传、视觉模型适配、隐私控制 |
| 前端 | `web/index.html` | 会话状态、设备选择、权限提示、移动端适配 |
| 运营后台 | `web/admin.html` | 独立后台 API、数字人/模型/日志管理、RBAC |
| 动作系统 | 现有自定义状态 + 新增动作状态机 | 语义/视觉事件、动作资产、优先级、打断和同步 |

### 6.2 推荐阶段

| 阶段 | 范围 | 达成效果 |
| --- | --- | --- |
| P0：可演示版 | 角色、文本/语音、手动打断/继续、4 种语言、摄像头预览、单次开场问候 | 可演示的一对一数字人对话 |
| P1：可用版 | 自动 VAD 打断、视觉问答、持久化会话、数字人创建/发布、模型路由、角色管理页面、设备选择、静默追问与勿扰控制、L1 语义动作 | 可用于导览、培训、展厅接待 |
| P2：生产版 | RBAC、密钥管理、限流、审计、内容安全、知识库、日志/告警、压测、容灾、外部业务事件驱动 | 可对外部署和运营 |

## 8. 依赖与风险

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 数字人端到端延迟 | 打断感和自然度下降 | 分段流式 LLM/TTS、VAD、GPU 基准测试 |
| 方言质量不稳定 | 用户体验不一致 | 逐语种验收矩阵；不达标时明确降级策略 |
| 摄像头隐私 | 合规与信任风险 | 显式授权、默认不存图、可见状态、短期缓存与删除策略 |
| LLM 幻觉/越权 | 错误回答或不当内容 | 角色边界、知识库引用、审核和拒答策略 |
| 主动打扰用户 | 反感、会话流失 | 默认低频、单会话上限、勿扰开关、仅对明确事件发言 |
| 断线会话丢失 | 无法恢复对话 | P1 将会话历史持久化，重连使用稳定会话 ID |
| 高并发 GPU 资源 | 服务不可扩展 | P2 引入队列、限流、会话配额与水平扩展 |
| 模型密钥泄露 | 第三方资源和账单风险 | 仅保存密钥引用/密文，前端永不返回原始密钥；记录所有变更审计 |
| 动作不自然或误识别 | 破坏真人感 | 先用少量高质量动作资产，多帧确认、频控和中性动作回退 |

## 9. 完成效果预期

在 P0 完成后，可交付一名具有指定形象、角色和音色的数字人：用户在桌面或手机浏览器建立 WebRTC 连接，数字人按角色主动问候一次；用户通过文字或语音提问，数字人以指定语言实时说话并同步口型；用户能打断、提出新问题或继续上一话题，并可打开本地摄像头。

在 P1 完成后，数字人能在用户插话时自动停下、理解用户主动提交的画面、跨重连恢复会话，并由后台配置多个角色与语言组合；在用户静默或出现经授权的业务事件时，按频率与勿扰策略主动展开或推进对话。

在 P2 完成后，运营人员可从统一后台创建、命名、测试、版本化发布和回滚数字人；每个数字人可以选择不同的 LLM、ASR、TTS 和视觉模型组合。后台会记录请求 ID、模型版本、耗时、错误与会话事件，并根据权限显示和导出数据。

动作能力成熟后，数字人会在“不会回答、欢迎、感谢、告别、拒答”等场景使用匹配的表情、手势和身体姿态；在用户授权摄像头并做出挥手、点头或离场动作时，数字人可做出对应回应。

“真人级自然交流”可在视觉、音色、延迟和打断体验上逐步逼近，但不能承诺所有方言、所有设备、所有网络条件下均达到真人无差别效果。最终质量取决于选定的 LLM、ASR/TTS 提供商、数字人模型、GPU 配置和验收样本。

## 10. 下一步决策

1. 确认首个落地场景及允许的角色边界。
2. 确认首批语言/方言和可接受的降级规则。
3. 选择视觉模型、LLM、ASR/TTS 的部署方式与数据合规区域。
4. 确认模型供应商清单、密钥托管方式及是否支持私有化模型端点。
5. 确认后台角色：平台管理员、运营管理员、内容管理员和只读审计员。
6. 以 P0 做真实设备、网络和端到端延迟验收，再决定 P1 投入。

## 11. 技术可行性与配置建议

### 11.1 结论

该功能在技术上可以实现。当前 LiveTalking 已能承担“音频驱动数字人 + WebRTC 输出”的核心渲染工作；拟人化反馈需要在前面增加动作决策层，在摄像头场景增加视觉事件识别层。最现实的路线是先做有限、高质量、可解释的动作集合，而不是一开始追求实时全身自由动作。

### 11.2 技术链路

```text
文本/ASR/视觉事件
        -> 会话状态机
        -> 语义与情绪分类
        -> 动作策略（优先级、打断、频控）
        -> 动作资产/表情/姿态参数
        -> TTS 音频 + avatar 驱动
        -> WebRTC 音视频
```

建议组件：

| 能力 | 首选实现 | 说明 |
| --- | --- | --- |
| 数字人视频 | LiveTalking + MuseTalk/Wav2Lip/Ultralight | 复用现有模型和 WebRTC，不替换主干 |
| 语音识别 | SenseVoice/FunASR + WebRTC/浏览器麦克风 | 增加 VAD、端点检测和语言路由 |
| LLM | OpenAI 兼容接口或私有模型 | 输出回答和结构化 `emotion/action` 事件，不让前端猜动作 |
| 动作决策 | Python 会话状态机 | 处理优先级：打断 > 拒答/安全 > 用户手势 > 普通情绪 > 待机 |
| 固定动作 | 预录动作片段、`audiotype`、表情参数 | P0/P1 最稳定、成本最低 |
| 手势识别 | MediaPipe Tasks 或同类姿态/手部模型 | 浏览器本地优先；服务端识别时只上传低频帧 |
| 视觉问答 | 视觉语言模型 | 与手势识别分开，按用户提问抓帧 |
| 日志 | 结构化 JSON + 请求 ID + PostgreSQL/ClickHouse | 记录事件、模型耗时、动作选择和失败原因 |

### 11.3 硬件配置

| 级别 | 推荐配置 | 适用范围 |
| --- | --- | --- |
| 本地演示 | NVIDIA RTX 3060 12GB 或同级；8 核 CPU；32GB RAM；SSD；千兆网络 | 单路、低分辨率、固定动作、云端 LLM/TTS |
| 推荐单机 | RTX 4090 24GB 或 A5000/A6000；12-16 核 CPU；64GB RAM；NVMe；稳定上行 | 1-3 路并发，实时 ASR、LLM、TTS 和数字人 |
| 生产拆分 | GPU 渲染节点 + ASR/视觉节点 + API/队列节点；每路 GPU 按基准压测扩容 | 多会话、视觉问答、后台运营和故障隔离 |

显存不能只按模型文件大小估算，还要包含推理 batch、视频帧缓存、音频队列和并发会话。最终并发数必须用目标 avatar、分辨率、帧率和 TTS 供应商做实测。

### 11.4 延迟目标

P0/P1 建议验收以下指标：

- 用户停止说话到数字人开始回应：普通网络下 1.5-3 秒。
- 用户点击打断到停止继续出声：目标小于 300ms，受浏览器缓冲和 TTS 分片影响。
- 固定语义动作与语音开始偏差：目标小于 150ms。
- 摄像头手势事件：采样、连续帧确认和推理完成目标 300-800ms；不宜承诺零延迟。

### 11.5 必须新增的后端能力

1. `ActionEvent` 结构：`request_id`、`session_id`、`source`、`intent`、`emotion`、`action`、`priority`、`expires_at`。
2. 动作状态机：动作可取消、可排队、可被高优先级事件抢占，并在语音结束后恢复待机。
3. 模型适配层：统一 LLM/ASR/TTS/视觉模型接口，后台只保存供应商和模型引用，不把供应商逻辑写进路由。
4. 摄像头权限和帧策略：显式授权、低频抓帧、多帧确认、超时回退、中止后立即停止上传。
5. 可观测性：为一次用户输入关联 ASR、LLM、TTS、动作和 WebRTC 日志。

### 11.6 现实边界

- 现有 LiveTalking 更擅长“音频驱动嘴型/头像”，并不天然提供实时全身骨骼、手部接触和视线控制。
- “无法回答时的为难动作”适合用意图分类 + 固定动作资产实现，可靠性高；完全自由生成的身体动作需要新的动作生成/驱动模型和更多素材。
- 摄像头可以识别挥手、点头、离开等事件，但无法证明真实握手，也无法保证复杂遮挡、逆光和多人画面下的识别准确率。
- 生产环境必须增加 HTTPS、鉴权、限流、密钥托管、内容安全、隐私同意和日志脱敏。

因此，推荐的可交付目标是：先实现 8-12 个高频语义动作和 4-6 个摄像头事件，在真实设备上完成延迟与误识别验收，再决定是否投入全身动作生成。

## 12. Breeze TTS 评估

### 12.1 程序用途

Breeze TTS 2 是 BreezeBlue 发布的开源权重文本转语音模型，目标是实时、富表现力的语音交互。仓库提供 PyTorch 推理代码、CLI 和 FastAPI 流式接口，接口输出单声道 24 kHz、s16le PCM 音频。

### 12.2 主要功能

| 功能 | 说明 | 对本项目价值 |
| --- | --- | --- |
| 实时流式合成 | FastAPI `/v1/audio/speech`，分块返回 PCM | 降低数字人首字节语音延迟，适合打断场景 |
| Voice Clone | 参考音频 + 精确文字稿复刻音色 | 可为每个数字人绑定稳定音色 |
| Voice Design | 用自然语言描述设计声音，不需要参考音频 | 适合创建数字人时快速生成音色方案 |
| Voice Direction | 保持音色同时控制语速、情绪、表达方式 | 可把“为难、关切、严肃、开心”等动作语义传给 TTS |
| Vocal Events | 中文支持 `[笑]`、`[叹气]`、`[咳嗽]` 等内联事件 | 能增强“哎呀，这个我不知道呀”等拟人表达 |
| 中英双语 | 单模型支持自然中文和英文 | 覆盖首批中英文场景 |

### 12.3 与 LiveTalking 的匹配度

匹配度为 **高（语音层）**。LiveTalking 现有 TTS 插件已经负责“文字 -> 音频帧 -> avatar 口型驱动”；Breeze 可以作为新的 TTS provider 接入，不需要改 WebRTC 和 avatar 渲染主干。

建议新增 `tts/breeze.py`：向 Breeze 的 FastAPI 流式接口发送文本、instruction、参考音频和参考文本；接收 24 kHz PCM 后按 LiveTalking 的音频 chunk 大小切片，写入 `parent.put_audio_frame`。需要处理采样率转换、请求取消、超时、单并发限制和错误回退。

动作编排层可以把同一个语义事件同时映射为：

```text
unknown_answer -> 文本“哎呀，这个我不知道呀”
                -> Breeze instruction“略带为难、轻松、短暂停顿”
                -> [叹气] 或 [笑] 等受控 vocal event
                -> avatar 的耸肩/摊手动作
```

### 12.4 配置要求

| 项目 | Breeze TTS 2 要求 |
| --- | --- |
| 操作系统 | Linux，Python 3.10+ |
| GPU | CUDA NVIDIA；约 7.7 GiB 显存用于 eager，约 14.4 GiB 用于 `--fast-all`；官方建议 12 GB 起步，快速路径建议 24 GB |
| 推荐硬件 | RTX 3060 12GB 可做单路演示；RTX 4090 24GB/A5000/A6000 更适合实时服务 |
| 服务形态 | 独立 FastAPI 服务，默认单并发，端口示例 7860 |
| 音频格式 | 单声道 24 kHz signed 16-bit little-endian PCM |
| 参考音频 | 声音克隆需要干净参考音频及精确文字稿 |
| 语言 | 当前 README 明确支持中文和英文；不应直接宣称支持粤语、上海话等方言 |

### 12.5 关键限制与风险

1. **商业许可阻断。** 仓库源代码是 Apache 2.0，但 Breeze TTS 2 模型权重、衍生模型和自托管输出受 BreezeBlue Research and Non-Commercial License 约束，仅限研究和非商业用途。若我们的平台面向商业客户，不能直接把自托管 Breeze 输出作为商业服务，必须取得单独商业许可或使用其付费托管 API。
2. **默认单并发。** 官方 API 使用全局锁拒绝并发请求，适合单路或串行语音服务；生产多会话需要多实例、队列和 GPU 配额，不能只提高 Web 服务器线程数。
3. **硬件和部署较重。** 需要 CUDA GPU、PyTorch 2.9.1、特定依赖和可能的 FlashAttention/CUDA 架构构建；不适合作为无 GPU 的轻量部署方案。
4. **中文/英文边界。** 它能增强普通话和英文表现力，但不能自动解决方言 ASR/TTS 质量问题。
5. **流式协议适配。** Breeze 返回裸 PCM，不是 WAV/MP3；LiveTalking 需要增加 PCM 缓冲、采样率和中断清理逻辑。

### 12.6 建议结论

- **研究/内部演示：推荐接入。** 它能显著提升音色设计、情绪表达、语音首包和拟人化 vocal event 能力。
- **商业生产：暂不直接采用自托管权重。** 先核实 BreezeBlue 商业许可或托管 API 条款；在许可未明确前，继续使用已有 Edge/Azure/腾讯/豆包等可商用 TTS 作为生产默认。
- **产品后台：可以预留 Breeze provider。** 在模型路由中加入 `breeze`，标记为“研究/非商业”或“需授权”，通过统一 TTS 接口做可插拔切换。
